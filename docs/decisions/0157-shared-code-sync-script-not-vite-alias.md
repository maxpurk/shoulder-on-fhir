# ADR-0157: Cross-frontend shared TypeScript via a sync script, not a Vite alias/shared package

**Date:** 2026-08-05
**Status:** Accepted
**Found via:** `docs/limitations_items/` — "Q11 research-follow-up offsets duplicated across the two frontends," logged 2026-08-02 and explicitly deferred at the time as "a larger structural change than this fix's scope." Picked up now, alongside porting the Constant-Murley POOS-15 sub-item calculator (ADR-0112) to the SDC frontend, which needed the same mechanism for a second, larger module (`constantScore.ts`).

## Context

Two independent pieces of logic were hand-duplicated between `frontend/` and `sdc-frontend/`, each a genuinely separate npm project with no existing workspace/monorepo tooling connecting them:

1. `Q11_TIMEPOINTS` (the five SECEC Q11.a-e research follow-up day-offsets) — duplicated in `frontend/src/lib/patientStage.ts` and `sdc-frontend/src/lib/bundleAssembler.ts`, kept in sync by hand (a real edit — adding the `code` discriminator field, 2026-08-04 — had to be applied to both copies manually in the same session that first logged this gap).
2. `constantScore.ts` (the ~260-line POOS-15 Constant-Murley sub-item derivation module, ADR-0112) — needed in `sdc-frontend` too for this session's SDC POOS-15 calculator port (ADR-0158), but existed only in `frontend/src/lib/`.

The obvious fix — a real shared package (npm/pnpm workspace) or a Vite `resolve.alias` pointing both projects at one file outside either `src/` — was investigated and found to break the actual deployment path: `docker-compose.yml` scopes each frontend's Docker build context to its own directory (`context: ./frontend`, `context: ./sdc-frontend`). A cross-directory import resolves fine under `npm run dev` (full local filesystem access) but the file simply isn't present inside either Docker build context, so the same import would fail — silently at `docker build` time, not at the point someone edits the shared file — the first time either frontend's Docker image actually got rebuilt.

## Decision

**A sync script (`tools/sync-shared-code.sh`), not a shared package.** Canonical source files live in a new `shared/` directory (`constantScore.ts`, `q11Timepoints.ts`). The script copies each into `frontend/src/lib/shared/` and `sdc-frontend/src/lib/shared/`, prepending a "GENERATED — do not edit, canonical source is shared/X.ts" banner comment to each copy. Both existing consumers (`patientStage.ts`, `bundleAssembler.ts`, `StepOutcomeScores.tsx`, `Q12PromForm.tsx`) now import from `./shared/...` (the synced copy) instead of a hand-maintained local definition.

The generated copies (`frontend/src/lib/shared/`, `sdc-frontend/src/lib/shared/`) are gitignored — the canonical `shared/` directory is tracked, the copies are regenerated by the pipeline, exactly the same treatment this project already gives `ig/fsh-generated/` (regenerated by `sushi .`) and `frontend/dist`/`sdc-frontend/dist` (regenerated by `npm run build`). `build-and-deploy.sh` runs the sync script automatically, immediately before the Docker build step, whenever `--rebuild-frontends` is passed — so a real deploy never ships a stale copy; only a local `npm run dev` after editing `shared/` without a manual sync run can drift, the same class of manual-step reliance this project already accepts for `sushi . && seed/load-profiles.sh` after an FSH edit.

## Alternatives Considered

| Alternative | Why not chosen |
|---|---|
| Vite `resolve.alias` + `server.fs.allow` pointing both projects at `../shared/` | Verified broken for the actual deployment path — Docker build context is scoped per-frontend-directory; the aliased file wouldn't exist inside either build context, so the deployed image would fail to build (or silently omit the import, depending on how Rollup handles a missing aliased path) the first time either image was rebuilt after this change. |
| Widen `docker-compose.yml`'s build `context` to the repo root, with a `dockerfile:` path into the frontend subdirectory | Considered — would let a real relative import work unmodified. Rejected: the repo root also contains `tools/validator_cli.jar` (~185 MB) and other large, irrelevant content that would then be sent to the Docker daemon as build context on every build (even though `COPY` commands stay scoped), a real, measurable build-speed regression for every future frontend rebuild, not just this one. |
| A real npm/pnpm workspace turning `frontend/`, `sdc-frontend/`, and a new `shared/` package into one monorepo | Rejected as disproportionate to this fix's scope — would touch both projects' `package.json`, lockfiles, and CI/deploy tooling assumptions throughout `build-and-deploy.sh`, for a benefit (2 shared modules, ~300 lines total) this simpler script already delivers. Could be revisited if shared surface area grows substantially. |
| Leave the duplication in place, accept the risk (status quo) | Rejected — the risk was already demonstrated live in this same session (the Q11 `code`-field addition had to be hand-applied to both copies), and this session separately needed a second shared module (`constantScore.ts`) for the SDC POOS-15 port, doubling the duplication surface if left unaddressed. |

## Consequences

✅ `Q11_TIMEPOINTS` and `constantScore.ts` each now have exactly one canonical definition; both frontends consume generated, clearly-marked copies.
✅ The generated copies are gitignored, matching this project's existing treatment of `fsh-generated/`/`dist/` — no risk of the canonical source and a stale generated copy both being tracked and silently diverging in git history.
✅ `build-and-deploy.sh --rebuild-frontends` (and `--full`, `--clean`, which imply it) always regenerates fresh copies before the Docker build — the authoritative deploy path can't ship a stale copy.
✅ `npm run build`/`npm run lint` clean on both frontends after the migration.
⚠️ Local `npm run dev` immediately after hand-editing `shared/*.ts`, without running `tools/sync-shared-code.sh` or `build-and-deploy.sh`, will serve the stale pre-edit copy — a real, if minor, rough edge; documented in the sync script's own header and in `shared/*.ts`'s own canonical-source banner comment.
⚠️ Not a general-purpose solution for arbitrarily large shared surface area — see the npm/pnpm workspace alternative above; revisit if more than these two modules end up needing this treatment.
