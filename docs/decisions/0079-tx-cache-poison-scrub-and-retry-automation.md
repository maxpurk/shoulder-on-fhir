# ADR-0079: Automatic tx.fhir.org cache-poison scrubbing + watchdog/retry across `validate.sh`, `--genonce`, and `validator-service`

**Date:** 2026-07-17
**Status:** Accepted; root-cause attribution corrected and §Decision 2/3/4 (the retry loops and the unconditional every-deploy `validator-service` scrub-restart) superseded by ADR-0080, same day. §Decision 1 (`tools/scrub-tx-cache.sh` itself) and §Decision 5 (the `set -e` bug fix) are unaffected and remain in force — see ADR-0080 for the control-test evidence and exactly what changed.
**Builds on:** ADR-0071 (validator-service resilience — first identified and documented the poisoned-cache failure mode, but left its recovery manual)
**Amends:** ADR-0071's Alternatives Considered (the "surgically edit poisoned entries" row, rejected there as too risky) and its Consequences ⚠️ line ("no code-level fix was found") — both superseded by this ADR's `tools/scrub-tx-cache.sh`.

## Context

ADR-0071 diagnosed that the FHIR Validator CLI's on-disk terminology cache (`tools/.tx-cache/`, shared between `tools/validate.sh` and `validator-service` via the `docker-compose.yml` mount) caches `tx.fhir.org` error responses exactly like successful ones. A single flaky `$cache-control` session poisons every lookup that session touched, replayed instantly from disk forever, until the cache is manually cleared. At the time, surgically removing just the bad records was considered and rejected as too risky — the cache file is an undocumented custom text format, and a parsing mistake during that investigation nearly produced a corrupted (0-byte) file. The adopted mitigation was a fully manual, documented recovery: stop `validator-service`, wipe the whole cache directory, restart.

Re-investigating this on 2026-07-17 (prompted by the same failure recurring across three separate commands in one session — `tools/validate.sh`, `validator-service`, and `--genonce`), direct inspection of the *live* cache on this machine showed the blast radius is worse than the 46/268 figure ADR-0071 recorded: **23 of 23 records were poisoned across every cache file** (`snomed.cache` 18/18, `all-systems.cache` 2/2, the tear-location CS cache 1/1, `iso3166.cache` 1/1, `loinc.cache` 1/1) — one bad session had poisoned lookups across every code system in use, not just SNOMED. At the time this read as confirming ADR-0071's assessment that `tx.fhir.org` poisoning is an ongoing reliability issue; **corrected the same day by ADR-0080**, once monitored more carefully: the single shared `$cache-control` session UUID behind all 23 poisoned records is exactly the fingerprint a single locally-stalled connection would leave, not 23 independent server-side failures.

Separately, `tools/validate.sh` had **no timeout at all** on the validator CLI's `java` invocation (unlike `validator-service`, which got a 90s `Future.get` timeout in ADR-0071) — a stalled call could hang the process indefinitely with zero console output, indistinguishable from a true hang, per the project guide's existing "don't be surprised if a run needs to be killed" guidance. The same was true of `build-and-deploy.sh --genonce`'s IG Publisher Docker invocation before its own `IG_PUBLISHER_TIMEOUT` watchdog was added (undated, prior to this session).

A live diagnostic during this session (direct `java -jar validator_cli.jar` run against the seed bundle, freshly scrubbed cache, brand-new terminology session, killed manually after ~4 minutes stuck at `Validate seed/bundles/example-patients.json` with no further output) was read at the time as a **second, distinct failure mode**: "a genuine live stall on `tx.fhir.org`'s side that is not explained by cache poisoning at all." **This specific claim is the one ADR-0080 directly disproves.** A follow-up control test — the identical command run on the deployment server, zero VPN in its network path — completed cleanly in 85 seconds the same day. Live `ps`/`lsof` capture of a repeat of the local stall showed near-0% CPU and sockets to `tx.fhir.org` stuck in `CLOSE_WAIT`, consistent with a local network path silently dropping the connection, not a server-side stall. See ADR-0080 for the full evidence chain. What remains true here: cache poisoning and connection stalls are two distinct problems, and the fix below (bounded watchdog instead of an indefinite hang) is the right response to a stall regardless of where it originates.

Whether to flip `TX_SERVER`/`IG_TX_SERVER` to offline-by-default was re-litigated in this session and rejected again, for the same reasons ADR-0048/ADR-0049/ADR-0071 already established (breaks SNOMED-coded `QuestionnaireResponse.answer.valueCoding` bind-checks on real clinical fields) — not revisited further here.

## Decision

1. **New script `tools/scrub-tx-cache.sh`.** Parses each `*.cache` file's record format (records delimited by an 86-dash line; the file always ends with a trailing delimiter and no content after it — CRLF line endings, which broke naive `grep '...$'` matching during development and required anchoring only on the leading dashes). A record is poisoned if its cached value contains `"class" : "SERVER_ERROR"` — this covers every error variant observed (expired-session errors, `SocketTimeoutException`), not just the one exact message ADR-0071 quoted. Rewrites each file with poisoned records removed; safe to run repeatedly (no-op once clean). Written in POSIX-ish bash (`grep`/`sed`, explicit line-number bookkeeping) rather than `awk`, because macOS's default `awk` (the one true awk) does not reliably support `{n,}` interval regex.
2. ~~**`tools/validate.sh` runs the scrub before every batch attempt**, and wraps the validator invocation in a background watchdog (`VALIDATE_BATCH_TIMEOUT`, default 300s) that kills the JVM if it's still running past the ceiling. On timeout or crash (no output file), it scrubs again and retries (`VALIDATE_MAX_ATTEMPTS`, default 2) before reporting a clean `BATCH CRASH` — closing the "no timeout at all" gap described above.~~ **Superseded by ADR-0080**: the watchdog/timeout is kept (good regardless of cause), but the automatic retry-after-scrub is removed — retrying doesn't fix a local network stall, it just doubles the wait before the same inevitable failure. `tools/validate.sh` now scrubs once and makes a single bounded attempt.
3. ~~**`build-and-deploy.sh --genonce` gets the same pattern** layered onto its pre-existing `IG_PUBLISHER_TIMEOUT` watchdog: scrub before each attempt, retry once by default (`IG_PUBLISHER_MAX_ATTEMPTS`, default 2) before falling through to the existing offline-fallback guidance (`IG_TX_SERVER=n/a` / raise the timeout).~~ **Superseded by ADR-0080** for the same reason as §Decision 2 — retry loop removed, single-attempt watchdog kept.
4. ~~**`build-and-deploy.sh`'s Docker-up stage now scrubs the shared cache before `validator-service` (re)starts, on every invocation** — not just under an opt-in flag. If `validator-service` is currently running, it's stopped first (it periodically flushes its in-memory cache back to disk and would silently overwrite an in-place scrub otherwise, per ADR-0071 §Decision 7), then the scrub runs, then the existing `docker compose up -d` brings it back. This extends coverage to the live pre-flight sidecar, which was explicitly left out of scope earlier in this session on the reasoning that touching a running container's cache was riskier than it was worth — re-evaluated and accepted given this is a testing/demo deployment with no data at stake, so a few seconds of `validator-service` downtime on every deploy is an acceptable cost for a self-cleaning cache. Verified live: injected a synthetic poisoned record into `loinc.cache`, ran a plain `./build-and-deploy.sh` with no flags, confirmed the container was stopped and restarted (uptime reset) and the poisoned record was gone afterward.~~ **Superseded by ADR-0080**: removed. Under the corrected diagnosis (local VPN, not `tx.fhir.org`), and with TX-dependent testing moved to the deployment server, cache poisoning should now be rare — restarting a container on every single deploy isn't worth the cost against a rare event. `tools/scrub-tx-cache.sh` stays available as an on-demand tool instead.
5. **Fixed a real bug found while building this**: `tools/validate.sh` runs under `set -e`, and the first version of the watchdog code had an unguarded `wait "$java_pid"` — when the watchdog killed the process, `wait` returned non-zero and `set -e` silently aborted the entire script right there, before the retry logic, the crash message, or the results summary ever ran. Fixed with `wait "$java_pid" 2>/dev/null || true`.

## Alternatives Considered

| Alternative | Why not chosen |
|---|---|
| Leave the manual stop → wipe → restart recovery as the only mitigation (ADR-0071's original decision) | Already shown not to work in practice — the cache was found 100% poisoned (23/23 records) at the start of this session, meaning the manual procedure wasn't being invoked reliably. Requires a human to notice the "instant error" symptom and remember the exact recovery sequence every time. |
| Surgically edit poisoned entries out by hand (rejected by ADR-0071 as too risky) | Revisited: the risk ADR-0071 flagged (a parsing mistake corrupting the file, as nearly happened during their investigation) is exactly what a tested, disk-verified script eliminates. This ADR's script was verified against the real cache (confirmed correct record boundaries, confirmed CRLF handling, confirmed byte-identical survival of non-poisoned records) before being wired into any automated path. |
| Flip `TX_SERVER=n/a` / `IG_TX_SERVER=n/a` as the new default | Re-rejected for the same reason as ADR-0048/ADR-0049/ADR-0071: breaks SNOMED-coded `QuestionnaireResponse.answer.valueCoding` bind-checks on real clinical fields (validator 6.9.7 treats these as hard errors offline). Not revisited in depth here since prior ADRs already settled it. |
| Use GNU `timeout`/`gtimeout` for the watchdogs instead of a background-sleep-and-kill subshell | Not available by default on macOS (no `coreutils`); the background-subshell watchdog pattern was already established by `--genonce`'s pre-existing `IG_PUBLISHER_TIMEOUT` implementation, so `tools/validate.sh` reuses the same portable pattern for consistency. |
| Scrub `validator-service`'s cache without stopping the container first | ADR-0071 already established the container periodically flushes its in-memory cache back to disk, silently overwriting on-disk edits made while it's running. Stopping first (cheap, ~1s) avoids a race that would make the scrub a no-op some of the time. |

## Consequences

✅ The specific failure mode ADR-0071 diagnosed but didn't fix — a failed session poisoning the cache permanently — now self-heals via a tested, on-demand script (`tools/scrub-tx-cache.sh`), whatever produces a poisoned entry.
✅ `tools/validate.sh` and `--genonce` can no longer hang indefinitely with zero feedback; both now fail within a single bounded window (300s / 900s) with a clear message. (ADR-0080 removed the 2-attempt retry described here — see that ADR.)
✅ Verified live end-to-end: real cache poisoning (23/23 records) was found and fixed; a synthetic poisoning test against `validator-service`'s cache was found and fixed by a plain `./build-and-deploy.sh` run.
⚠️ **Corrected by ADR-0080:** the line originally here read "this does not fix `tx.fhir.org`'s underlying unreliability... a stall can occur... on `tx.fhir.org`'s side." A same-day server-side control test (identical command, zero VPN in that machine's path, 85s clean completion) directly disproves the "on `tx.fhir.org`'s side" attribution — the stall was this developer machine's VPN tunnel. `tx.fhir.org` itself was never confirmed unreliable; every isolated call to it, tested in isolation, succeeded in under a second.
⚠️ ~~`build-and-deploy.sh` now briefly stops and restarts `validator-service` on every invocation, including a plain no-flag run~~ — **reverted by ADR-0080**: this is no longer the case. The scrub-before-restart is on-demand only now.
⚠️ The exact mechanism behind the live (non-poisoned-cache) stall observed in this session was subsequently identified by ADR-0080 (local VPN tunnel, reduced MTU, silently dropping longer-lived connections) — no longer unidentified/future work.
