# ADR-0120: Triage of the IG Publisher's own QA report (81 errors) — one real fix, rest are tool limitations

**Date:** 2026-07-31
**Status:** Accepted

## Context

`build-and-deploy.sh --genonce` (and `--full`) runs the HL7 IG Publisher to build the HTML documentation site. It produces its own QA report (`ig/output/qa.json`/`qa.txt`/`qa.html`), separate from and in addition to `tools/validate.sh`'s FHIR Validator CLI run (ADR-0024) — the authoritative conformance gate, which stayed at 0 errors throughout this investigation. The IG Publisher's own report showed **81 errors, 435 warnings, 255 hints** on every recent build (identical count on both a warm-cache and a fully-cold `--full` run on the deployment server, 2026-07-31 — ruling out cache state as a factor). This ADR triages that count. None of it affects the resources HAPI stores or either frontend submits — it is entirely about the generated documentation website's internal cross-references.

Pulled `ig/output/qa.txt` and categorized every `^ERROR` line (321 raw lines — see the "extra details" note below for why the raw grep count exceeds the 81 summary figure):

1. **~228 broken `item.definition` anchor links**, all on the three Questionnaire HTML pages (`Questionnaire-shoulder-registration.html` 144, `-follow-up.html` 69, `-surgery.html` 15, plus ~44 more reported via a second `Questionnaire.text.div: Hyperlink '...'` check on the same underlying links). Example: `StructureDefinition-shoulder-abduction-observation.html#Observation.valueQuantity` — the target *page* exists (confirmed: it lists hundreds of valid anchors), but that specific *anchor* doesn't resolve. Root cause: when a profile constrains `value[x]` down to exactly one type (as every derived Observation profile in this IG does — ADR-0008), the IG Publisher's own anchor-ID generation for that element doesn't consistently match the type-specific fragment (`...valueQuantity`, `...valueCodeableConcept`) that `Questionnaire.item.definition` URLs use to reference it. This reproduces on every profile with a fixed `value[x]`, i.e. essentially all 57 derived Observation profiles referenced from the three Questionnaires' `item.definition` fields.
2. **~12 broken links to renamed/retired resources** on `profiles.html`, `terminology.html`, one on `StructureDefinition-shoulder-imaging-study.html`: `pain-severity-observation`, `occupation-observation`, `inspection-observation`, `CodeSystem-satisfaction-scale` — none of these strings exist anywhere in current FSH/markdown source (confirmed via repo-wide grep). They predate the ADR-0086 (inspection split into Atrophy/Deformity/NormalShoulderContour), ADR-0087 (pain split into 4 context-specific axes), and ADR-0070 (satisfaction migrated to LOINC, local CodeSystem retired in place as a comment-only placeholder) redesigns. `ig/output/qa.compare.txt` confirms the IG Publisher does its own version-to-version comparison against a previously published version — these are that comparison surfacing links to artifacts that intentionally no longer exist, not live authoring mistakes. One further error (`AcquisitionModality (missing link)` on the imaging-study page) is a broken reference into the external DICOM base spec, unrelated to this project's own authoring.
3. **2 CodeSystem "extra details" errors** (`GoutallierClassificationCodes`, `CofieldTearSizeClassificationCodes`): "CodeSystem ... has an 'all system' value set ... but the include has extra details." Both `content = #complete` CodeSystems get an implicit "all codes" ValueSet from FHIR itself; this project also hand-authors an explicit ValueSet for each that inlines every concept's display text directly (`* GoutallierClassificationCodes#0 "Grade 0 – Normal muscle"` etc.) rather than a plain `include codes from system X`. The FSH source's own comment explains why: avoiding a Lucene-on-tmpfs race at `$expand` time after a HAPI restart (an unpopulated Lucene index returning 0 concepts, see ADR-0031/ADR-0063). The IG Publisher's static checker flags the per-concept display enumeration as "extra details" that make it not-quite-recognizable as a clean "all codes" include, even though it resolves to the same code set.
4. **3 `sdc-2` constraint failures** (one per Questionnaire): `sdc-questionnairecommon` (the profile all three Questionnaires declare via `sdc-questionnaire-extr-defn`) requires `Extension:artifact-versionAlgorithm` whenever `Questionnaire.version` is set. All three Questionnaire instances set `version` (`"0.2.0"`/`"0.1.0"`) without it — a genuine, currently-failing profile constraint, unlike the other three categories.

## Decision

1. **Fixed category 4** (the only real defect): added `* extension[http://hl7.org/fhir/StructureDefinition/artifact-versionAlgorithm].valueCoding = http://hl7.org/fhir/version-algorithm#semver` to all three Questionnaire instances (`ShoulderRegistrationQuestionnaire.fsh`, `ShoulderSurgeryQuestionnaire.fsh`, `ShoulderFollowUpQuestionnaire.fsh`) — `semver` is the correct code for this IG's `MAJOR.MINOR.PATCH` versioning (confirmed against the extension's bound ValueSet, `http://hl7.org/fhir/ValueSet/version-algorithm`, cached locally from `hl7.fhir.uv.xver-r5.r4#0.1.0`, an already-declared IG dependency). Verified via `sushi .`: 0 errors, 0 warnings, extension present in the compiled JSON with the expected `valueCoding`.
2. **Categories 1–3 are not fixed** — documented here instead, per the reasoning below, so a future maintainer (or the author, months later) doesn't re-diagnose the same 81-minus-3 count from scratch:
   - Category 1 (broken `item.definition` anchors) is an IG Publisher rendering limitation with fixed-`value[x]` profiles, not something under this project's control to correct from the FSH side — the anchors it's trying to generate/match are its own internal HTML-generation behavior. Revisit if a future IG Publisher release changes its anchor-ID scheme for sliced/typed `value[x]` elements.
   - Category 2 (stale comparison-links) is expected behavior of the IG Publisher's own version-history diffing, not a defect — fixing it would mean either scrubbing genuinely accurate historical comparison data or fighting a tool feature, neither of which is worth it for a `status: draft`, unpublished IG with no real prior public version to preserve compatibility with.
   - Category 3 (CodeSystem "extra details") is a **deliberate, already-adopted tradeoff** (the Lucene-race workaround) — reverting the inline concept enumeration to satisfy this specific IG Publisher nitpick would reintroduce the `$expand`-returns-0-concepts bug it was written to prevent. Not worth trading a real runtime bug for a cosmetic documentation-site warning.

## Consequences

✅ The one genuine FHIR profile-conformance defect this investigation found (`sdc-2`) is fixed, at essentially zero cost (3 one-line additions, verified compiling clean).
✅ The remaining ~78 errors are now triaged and explained rather than an unexamined "81 errors" figure — future correspondence about this IG's QA status can point here instead of re-investigating.
⚠️ The IG Publisher's own QA count will still report roughly 78 errors after this fix — expected and understood, not a regression signal to chase. If that count changes meaningfully on a future build, that's the signal worth investigating (a new, different problem), not the baseline itself.
⚠️ Category 1's broken narrative links are a genuine (if low-severity) documentation-quality gap in the published IG website: a reader clicking an `item.definition` cross-reference link on any of the three Questionnaire pages lands on the right StructureDefinition page but not scrolled to the specific element. Logged in `docs/limitations_items/`.
