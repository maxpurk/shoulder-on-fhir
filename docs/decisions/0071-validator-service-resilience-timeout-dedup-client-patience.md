# ADR-0071: Validator-service resilience — bounded concurrency, single-flight dedup, and a client-side patience limit

**Date:** 2026-07-11
**Status:** Accepted; root-cause attribution in §Context/§Consequences corrected by ADR-0080 — the "tx.fhir.org being unreliable" / "ongoing tx.fhir.org reliability issue" language below described a local VPN/MTU interaction on the developer's own machine, not the external server (see ADR-0080 for the control-test evidence: an identical run on the deployment server, zero VPN in its path, completed cleanly in 85s). The symptoms recorded here were real; the cause named for them was not. The mechanisms this ADR built (bounded pool, timeout/503, dedup, client-side abort + fail-open) are unaffected by that correction and remain in force.
**Builds on:** ADR-0051 (validator sidecar creation)
**Amends:** ADR-0051's Consequences section — the ⚠️ memory/footprint concerns there are unchanged, but its concurrency model (unbounded, un-timed `engine.validate()` calls on a fixed 4-thread pool) is superseded by this ADR.
**Amended by:** ADR-0079 — the poisoned-cache failure mode diagnosed in §Context point 2 and the "surgically edit poisoned entries" row it rejected in §Alternatives Considered are both superseded: a tested `tools/scrub-tx-cache.sh` now does exactly that (on-demand — ADR-0080 removed the automatic-on-every-deploy trigger this note originally described). Also amended by ADR-0080 (root-cause correction, see Status above).

## Context

A live registration submission exposed that `validator-service`'s original design (ADR-0051) had no timeout on `engine.validate()` and a hardcoded 4-thread pool with no separation between accepting HTTP connections and doing validation work. A slow or stuck validation — at the time attributed to `https://tx.fhir.org/r4` being unreliable, corrected by ADR-0080 to a local VPN/MTU interaction on the developer's machine — could hang a request indefinitely; when Nginx or the browser eventually severed that connection, the sidecar's own attempt to write a response produced `java.io.IOException: Broken pipe` / `insufficient bytes written to stream in FixedLengthOutputStream.close()`.

Live diagnosis (concurrent `curl` load bursts; JVM thread dumps via `kill -QUIT` since the runtime image is JRE-only with no `jstack`/`jcmd`) confirmed requests genuinely queue behind the 4-thread limit, and that the JVM heap was already ~77–89% utilized at idle just from holding the loaded IG/terminology packages — concurrent `engine.validate()` calls compete for a tight, shared heap.

Adding a per-call timeout (`VALIDATE_TIMEOUT_SECONDS`) surfaced two further problems:

1. **The terminology-cache session (`$cache-control?mode=start`) appeared unreliable** — it could expire mid-run or never fully succeed, producing `SERVER_ERROR` issues (`"the cache 'X' is not known to this server"`). (ADR-0080: this session-level failure is consistent with a VPN-tunnel connection drop mid-session, not a `tx.fhir.org`-side fault — every isolated call to the session endpoint itself, tested directly, succeeded in under a second.)
2. **Worse: the HL7 validator's local on-disk terminology cache (`tools/.tx-cache/`) caches error responses exactly like successful ones.** A single failed session poisons that specific lookup permanently — replayed instantly with no further network call — until the cache is manually cleared. Confirmed by direct inspection of `tools/.tx-cache/snomed.cache`'s record format (entries separated by an 86-dash line); 46 of 268 records contained a poisoned `"is not known to this server"` payload from a single incident. Fresh poisoning was observed recurring within the same session, including from the engine's own startup terminology-capability checks — at the time read as an ongoing `tx.fhir.org` reliability issue; ADR-0080 traces this to the same local network path rather than the server.

Without deduplication, a client retry of a still-in-flight validation started a second, fully redundant `engine.validate()` call competing for the same tight heap — investigated and closed with single-flight dedup.

Separately, whether `validator-service` should switch to offline terminology mode (`TX_SERVER=n/a` — an existing, ADR-0048/ADR-0049-precedented fallback already used by `tools/validate.sh`) to remove the `tx.fhir.org` dependency entirely was investigated in depth. Two Explore passes over the actual frontend code confirmed the SDC frontend (`sdc-frontend/`, port 3001) submits the raw `QuestionnaireResponse` resource (via `FlowPage.tsx` → `assembleBundle` → `bundleAssembler.ts`) with SNOMED-coded `item.answer.valueCoding` on 9 real clinical fields across all three Questionnaires (diagnosis, etiology, prior-treatment category/type, hand dominance, tendons involved, encounter/procedure type). This is exactly the `Questionnaire.answer.valueCoding`-with-SNOMED gap ADR-0049 found unacceptable enough to reverse `tools/validate.sh`'s own default away from offline mode (validator 6.9.7 special-cases this combination and throws hard errors, not soft warnings, in `-tx n/a` mode). Since both frontends share one `validator-service` instance — and ADR-0051 already established that a single instance sits right at this host's memory ceiling — running a second, offline-mode instance for just the unified frontend likely doesn't fit.

Finally, a live incident during testing showed the actual, concrete cost of getting this wrong: a pre-flight check hung long enough that the user closed the browser tab out of impatience. Nginx logged a `499` (client closed the connection); because the frontend's fail-open logic lives entirely in JavaScript that only runs if the `fetch()` call actually resolves (success, error response, or a timeout), the tab closing skipped that logic completely and the submission was lost — the patient had to be re-entered.

## Decision

1. **`validator-service` separates HTTP dispatch from validation work.** The HTTP server's own executor (accepting connections, cheap I/O) is now a `CachedThreadPool`; actual `engine.validate()` calls run on a separate, bounded pool sized by `VALIDATOR_THREADS` (default 4, kept conservative — the shared `engine`/heap means raising this without confirmed memory headroom risks OOM, not more throughput).
2. **Every validation is wrapped in `Future.get(VALIDATE_TIMEOUT_SECONDS, TimeUnit.SECONDS)`** (default 90). On timeout, the sidecar responds immediately with a clean `503` + `OperationOutcome` (`"validation exceeded Ns timeout"`) instead of leaving the connection open until Nginx or the client severs it. The abandoned `engine.validate()` call is not cancelled (no cooperative cancellation exists in the underlying engine) — it finishes in the background and its result is discarded.
3. **Single-flight deduplication.** `handleValidate` computes a SHA-256 key over the request body + profile params and looks it up in a `ConcurrentHashMap<String, CompletableFuture<OperationOutcome>>` (`inFlight`). A new key starts a `CompletableFuture.supplyAsync` on the bounded validation pool; an existing key is joined instead of starting a redundant computation. Entries are removed only via `whenComplete` — when the underlying computation itself finishes — not when any individual caller's wait times out, so any number of retries of the same content share the one real computation rather than piling up competing ones.
4. **HTTP accept backlog raised from OS-default (`0`) to `128`**, so a burst of connections queues at the socket instead of being refused while validation threads are busy.
5. **Both frontends apply a client-side timeout to the validator fetch call**, independent of and much shorter than the backend's own timeout: `AbortSignal.timeout(VALIDATE_CLIENT_TIMEOUT_MS)` (20s) in `frontend/src/lib/fhirClient.ts` and `sdc-frontend/src/lib/fhirClient.ts`. An abort surfaces as an `AbortError`, already caught by the existing `catch (err) { throw new ValidatorUnavailableError(...) }` block — no changes needed to `preflightValidate.ts` in either frontend, since it already treats `ValidatorUnavailableError` as fail-open-with-one-retry (ADR-0051). This decouples "how long the user waits" from "how long the backend keeps working": fail-open now reliably fires within roughly 20–45 seconds (one attempt plus the existing one retry) regardless of how slow `tx.fhir.org` or the backend is, so a user is very unlikely to close the tab before fail-open has already run and the submission has gone through directly.
6. **`TX_SERVER` stays on live `https://tx.fhir.org/r4` for both `validator-service` and `tools/validate.sh`.** Offline mode was investigated and explicitly rejected — see Alternatives.
7. **`tools/.tx-cache/`'s poisoned-entry failure mode and its recovery procedure are documented in the project guide**, alongside the existing cache-wipe guidance from ADR-0024/ADR-0049: symptom (an error that returns *instantly*, with no network delay, and doesn't go away on retry — the instant response is the tell that it's a poisoned cache entry, not a live failure), and the safe recovery order (stop `validator-service` first — it periodically writes its in-memory cache state back to the mounted disk directory, so editing/restoring cache files while it's running gets silently overwritten — then wipe `tools/.tx-cache`, then restart).

## Alternatives Considered

| Alternative | Why not chosen |
|---|---|
| Switch `validator-service` to `TX_SERVER=n/a` (offline terminology mode) | Confirmed via code inspection: breaks the SDC frontend's SNOMED-coded `QuestionnaireResponse.answer.valueCoding` fields (validator 6.9.7 treats these as hard errors offline, not soft warnings) — the same gap ADR-0049 found unacceptable for `tools/validate.sh`. 9 real clinical fields affected across all three Questionnaires. A second, offline-only sidecar instance for just the unified frontend likely doesn't fit this host's memory budget (ADR-0051). |
| Rely on a long backend timeout alone (600s tried first), no client-side limit | Doesn't stop a human from getting impatient and closing the tab mid-wait, which skips the JS-based fail-open path entirely — this is what caused the lost submission that prompted this ADR. Confirmed live: even a small, simple bundle can hang the full backend timeout on a bad `tx.fhir.org` day, independent of bundle size. |
| Surgically edit poisoned entries out of `tools/.tx-cache/snomed.cache`, keep the rest | Technically the best-preserved outcome (46 bad records out of 268), but the cache file is an undocumented, custom text format (entries delimited by an 86-dash line, CRLF line endings). A parsing mistake during investigation already produced a near-miss (a 0-byte file, caught before being applied). Not worth the risk for a problem the wipe-and-rewarm procedure already resolves adequately. |
| Permanently wipe `tools/.tx-cache/` as standing policy (not just one-time recovery) | A fully cold cache makes every terminology check a live network round-trip; measured directly at over 600s for a single moderately-sized bundle, still incomplete. Acceptable as a one-time recovery step; unacceptable as a standing policy — regresses every cold start back to this cost. |
| `TerminologyClientContext.setCanUseCacheId(false)` (disable `tx.fhir.org`'s server-side session-batching entirely) | Tried and reverted. Live testing proved it neither prevents hangs (a clean-cache, fully stateless-call test still hung the full backend timeout) nor reliably prevents cache poisoning (fresh poisoned entries still appeared with the flag active, including from the engine's own startup checks). An internal, undocumented library API with a real cost (slower per-call, no session-batching benefit) and no confirmed upside. |

## Consequences

✅ A stuck or slow validation can no longer hang a request indefinitely — bounded by `VALIDATE_TIMEOUT_SECONDS` on the backend and `VALIDATE_CLIENT_TIMEOUT_MS` on the frontend, whichever fires first.
✅ Retries of the same content no longer pile up redundant, competing validations against the same tight heap.
✅ A slow or stuck sidecar call now resolves into the existing fail-open banner path within roughly 20–45 seconds from the user's perspective, instead of up to (previously) 10 minutes — directly closing the "user gives up and closes the tab, losing unsaved data" failure mode this ADR was prompted by. (Verified working exactly as designed in the session that produced ADR-0080: a stalled local run hit fail-open on schedule and the submission went through.)
✅ Neither frontend's validation scope or correctness changed — `tx.fhir.org` stays live for both, so the SDC frontend's SNOMED-coded questionnaire fields keep full validation fidelity; no regression there.
⚠️ **Corrected by ADR-0080:** this ADR's original framing here blamed "`tx.fhir.org`'s underlying unreliability" for the observed hangs. The server-side control test in ADR-0080 shows `tx.fhir.org` itself was not the fault — the actual cause was a local VPN tunnel's reduced MTU silently stalling longer-lived connections on the developer's machine. This ADR's resilience mechanisms remain correct and useful regardless (any call to an external, best-effort, no-SLA service warrants bounded timeouts and graceful degradation) — only the diagnosis of *why* calls were stalling was wrong.
⚠️ `tools/.tx-cache/`'s poisoned-entry failure mode can still recur (the underlying HL7 library caches error responses as if they were permanent, whatever produces one) — `tools/scrub-tx-cache.sh` (ADR-0079) now fixes this with a tested script rather than the fully-manual wipe this ADR originally documented; ADR-0080 moved its invocation from automatic-on-every-deploy back to on-demand. This project's shared `tools/.tx-cache/` mount still means a poisoning event from a long sidecar validation can affect `tools/validate.sh`'s CI-gate cache too.
⚠️ The HTTP dispatch pool (`Executors.newCachedThreadPool()`) is unbounded — a very large burst of concurrent connections could spawn many dispatch threads, each blocked up to `VALIDATE_TIMEOUT_SECONDS` waiting on the bounded validation pool. Acceptable at this project's actual scale (a handful of demo users, not adversarial production traffic); worth revisiting if that assumption changes.
